## 1. 目的与范围

### 1.1 解决什么

上游 `aden-naming-standard` 解决的是**单个对象叫什么**（载体层命名式、编号线、状态后缀、受控值）。它没有规定**一批对象如何组织成一个项目**，也没有为 IT 治理文档以外的场景（科研、个人发展、Agent 打磨）提供取值。本规范补齐这几层：

1. **结构层**：一套跨场景通用的项目目录骨架（§3）；
2. **扩展层**：按上游 §9.3 规程登记的新受控取值（见 `docs/02`）；
3. **命名应用层**：文档名称的双形态与场景选名（`docs/04`）、9 类命名对象全景与 AI 选式路由（`docs/05`）。

### 1.2 不规定什么

1. 单个文件/目录的命名式细节 —— 以上游 §5 为准；
2. 存量目录的整改 —— 继承上游 §1.3，不重命名、不迁移；
3. 数据平台对象、ISMS 文件编号、集团文档类型 —— 以上游规范为唯一权威；
4. 具体场景的业务内容 —— `docs/03` 只给取值投影，不代替领域方法论。

### 1.3 与上游规范的关系

```
上游 aden-naming-standard v1.4  ── 命名式、字符纪律、状态后缀、编号线、受控值骨架
              │ 复用（不改一字）
              ▼
本规范 USP v1.1  ── 目录骨架 + 按 §9.3 登记的新取值
              ├── docs/02 扩展取值登记表 ── 本地 Draft，升级需治理侧确认
              ├── docs/04 文档名称方案 ── 双形态 + 场景选名（本规范 A1 细目）
              └── docs/05 完整命名体系 ── 9 类命名对象全景 + AI 选式路由
```

**冲突处理**：本文与上游规范冲突时，**以上游规范原文为准**；`docs/04`–`05` 与本文冲突时，命名细目以 `docs/04`（文档名称）/ `docs/05`（其他对象）为准。

## 2. 三轴与分层

继承上游 §4.1 三轴，用于校验每个新增目录与文件是否站得住：

```
轴 1｜是什么 —— 阶段（六段骨架之一）+ 类型（文档类型受控值）
轴 2｜属于谁 —— 域（业务域 / 学科域 / 技术域）
轴 3｜第几版 —— 版本 + 状态 + 日期
```

两层各自独立，不应互相套用：

| 层 | 对象 | 唯一性范围 | 取值来源 |
| --- | --- | --- | --- |
| 载体层 | 文件、目录、工作流实例 | 路径内 | 上游 §9 + 本规范 `docs/02` |
| 内容层 | 文档内标识码 | （类型 × 域）× 文档 | 上游 §7 |

## 3. 通用六段骨架（核心条款）

### 3.1 段定义

每个项目根目录下的**一级子目录**应为下列六段，编号两位、连字符后接英文阶段名（`NN-English`）。写法借鉴上游技术域编号（附录 A.2）的两位段码，**但分隔符按上游 §5.2 用连字符**，不用该附录存量值中的下划线（差别见 §7）。

| 段码 | 目录名 | 中文 | 语义 | 完成判据（可进入下一段的条件） |
| --- | --- | --- | --- | --- |
| `00` | `00-Ingest` | 输入 | 收集原始材料：选题、文献、干系人、现状资产、用例边界 | 输入清单登记完毕，来源可追溯 |
| `10` | `10-Analyze` | 分析 | 建模、拆解、逆向解析、路径规划、框架设计 | 分析结论成文，关键假设显式标注 |
| `20` | `20-Build` | 构建 | 写出产物：代码、规格、报告初稿、复刻实现、科研执行 | 产物达到可验证状态 |
| `30` | `30-Verify` | 验证 | 测试、评审、对齐校验、UAT、答辩预演 | 验证记录齐备，缺陷有归属 |
| `40` | `40-Deliver` | 交付 | 上线、发布、提交、归档、定稿 | 交付物有版本与状态，接收方确认 |
| `50` | `50-Sustain` | 沉淀 | 复盘、经验库、复用资产、版本迭代、持续跟踪 | 可复用项已登记，回流到相关段 |

### 3.2 回流段

`50-Sustain` 在目录树上占一级位置，但在工作流语义上是**回灌到前五段**的，不应理解为"最后才做的一步"。它在目录中排在末位只为排序稳定。

### 3.3 空段处理

某场景在某段无内容时，**应保留空目录并放一份 `README.md` 说明为何为空**，不应删除该段目录。理由：骨架完整性是 AI 识别与结构校验的前提；缺失段会让校验器无法区分"跳过"与"遗漏"。

### 3.4 主链不可逆序

`00`→`40` 为主链，产物在段间的推进方向**应**单向向前。`50` 可向任意段回流。跨段回退（如 `30` 退回 `20`）**应**在 `50-Sustain` 留一条记录，说明回退原因。

## 4. 目录树规则

### 4.1 单一场景

一个项目根目录 = 一套六段骨架 + 三个自描述文件：

```
<项目根>/
├── AGENTS.md              ← 场景声明（静态，AI 入口）
├── README.md              ← 人类可读总览
├── 00-Ingest/
├── 10-Analyze/
├── 20-Build/
├── 30-Verify/
├── 40-Deliver/
├── 50-Sustain/
└── .workbuddy/context/    ← 动态状态（context-persistence 引擎）
    └── task_state.json
```

### 4.2 混合场景

混合场景**不应**为每种场景复制一套六段目录。应按以下两种方式之一处理：

1. **并行实例**：一个项目根下开多个工作流实例，实例目录命名 `W<nn>-<主体>`（`nn` 两位补零，`W` 为工作流实例码，见 `docs/02`），每个实例内嵌完整六段骨架；
2. **阶段内并行**：若多个场景共享同一骨架的不同阶段（如"盘点+逆向+复刻"实为一条链），则它们本就是同一实例的连续阶段，**不应**再分子目录，直接在对应段内用文档类型受控值区分。

> 判据：若两条工作流**共享同一份输入与结论**，用方式 2；若**各自独立成链**，用方式 1。

> **落地提示**：`scaffold.py` 1.1.1 起可用 `--instance W01-<主体>:<场景>` 一次生成根级共享六段与各实例六段；不给该参数时按两步法对每个实例目录各跑一次脚本。只声明 `mix_mode: parallel` 而无实例目录时，校验器给 WARN、不硬判违规（见 `docs/03` §3）。

### 4.3 二级目录

六段之下的二级目录**宜**按文档类型受控值或业务/学科域组织，**不宜**再按阶段嵌套。三段以上的深度**应**在 `AGENTS.md` 中说明理由。

### 4.4 命名套用

- 文件名套上游 §5.1 命名式时，**阶段由所在目录定位**（如 `00-Ingest/`），不重复写进文件名；域段取受控域码。例如 `00-Ingest/` 下放 `AGI-InformationNote-Software-需求访谈纪要-v1.0-Draft.md`。文档类型与域段用**载体形**（`InformationNote`，见 `docs/04` §1）；
- 状态后缀只用上游 §5.6 五值，置于版本之后；
- 禁止空格与全角符号（上游 §4.3-3）；
- 段间分隔**应**用连字符，新产物**不应**引入下划线；下划线仅见于上游 §5.9 数据对象（其自身例外）。

## 5. 自描述文件（AI 识别契约）

### 5.1 三项自描述契约

| 契约 | 通道 | 内容 | 变更频率 |
| --- | --- | --- | --- |
| `AGENTS.md` | 静态前缀 | 场景类型、六段映射、当前阶段、命名规范指针 | 场景变更时才改，改后字节级冻结 |
| `.workbuddy/context/task_state.json` | 动态状态 | 目标、进度、子目标、待决问题、产物 | 每轮追加 |
| 命名校验入口 | 按需 | 指向 `aden-naming-standard` 的 lint 脚本 | 不变更 |

### 5.2 AGENTS.md 必含字段

根目录 `AGENTS.md` **应**含以下字段，供 AI 零交代接手：

1. **场景声明**：`scenario: <受控值>`（见 `docs/03`）；
2. **骨架说明**：六段各是什么、本项目当前在哪一段；
3. **命名规范指针**：`aden-naming-standard v1.4` + 本规范版本；
4. **扩展取值指针**：指向 `docs/02`，声明本项目用到哪些扩展值；
5. **状态读取指令**：从 `task_state.json` 读动态状态，不把状态写进本文件。

### 5.3 静态与动态分离

`AGENTS.md` **不应**写入 time / progress / status 等动态字段。理由：静态前缀一变，KV Cache 逐层失效；状态每轮追加才符合缓存友好布局（继承 `context-persistence` 注入契约）。

## 6. 编号规则

### 6.1 段码

六段段码 `00`–`50`，间隔 10，为未来插入新阶段预留（例如 `05` 段）。段码**不**连续流水，**不应**为"补齐"而重编号。

### 6.2 工作流实例码

`W<nn>`，两位补零，项目内唯一。唯一性范围 = 项目根内（继承上游 §6.1）。

### 6.3 其他编号

文档登记、内容层标识码、ISMS 编号等**一律**沿用上游 §6、§7 的既有编号线，**不**另造新线。

---

## 7. 字符纪律

继承上游 §4.3 全文：

1. **不应**使用国别字符；每个字符应能在任意键盘输入；
2. 复合名宜每部分仅首字母大写、其余小写；
3. **不应**使用空格与全角符号；
4. 段内分词靠大小写，段间分隔靠连字符。

**与上游附录 A.2 的差别**：技术域取值（如 `00_FrontEnd`）是上游**存量受控值**，其中下划线按 §1.3 豁免；本规范的段码是新产物，**应**用连字符（`00-Ingest`），不适用该豁免。二者形近而来源不同，不应互相援引。

## 8. 合规与审计

### 8.1 校验器

`tools/structure_lint.py` 校验三项：

1. 六段目录齐全（空段有 `README.md` 视为齐全）；
2. `AGENTS.md` 必含字段齐备（§5.2）；
3. 文件命名合规 —— 调用 `aden-naming-standard` 的权威 lint，不另写命名规则。

### 8.2 审计纪律

- 校验器只扫新建资产，存量标豁免（继承上游 §10.2）；
- 校验器跑不起来时，**只报"校验未完成"**，不得输出合规判定（继承上游 §5.1）；
- 退出码：0 = 无 ERROR；1 = 有 ERROR。

### 8.3 变更影响

改本规范 → 同步 `docs/02` 登记表、`docs/03` 投影表，检查 `docs/04`/`docs/05` 是否受影响 → 跑 `structure_lint.py` 与上游 lint → 版本号格式遵循上游 §5.4，递增记入下方修订记录。
